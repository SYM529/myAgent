# 问题排查手册：开发全过程中遇到的问题与解决方案

> 记录本项目从零到公网部署过程中遇到的真实问题。每条按「现象 → 根因 → 解决」组织，
> 都能在仓库的提交历史、评测报告或 README 相应章节中找到佐证。
> 这些问题覆盖了 LLM 应用开发最典型的几类坑：**非确定性、安全与能力的边界、
> 多组件时序、国内网络环境、Windows 开发环境**。

---

## 一、评测体系与 Prompt 工程

### 1.1 评测配置错误：安全用例整批被误杀

- **现象**：首轮全量评测通过率只有 67.9%，`prompt_injection` 类别几乎全军覆没。
- **根因**：不是模型安全能力差——是评测配置错误：`expect_tools: []`（不期望调用工具）
  配上 `tool_match: any` 的判定语义，空集求交必然判负，整个类别被系统性误杀。
- **解决**：修复判定逻辑，通过率 67.9% → 96.2%。
- **教训**：看起来是"模型不行"的问题，先怀疑测量工具本身。

### 1.2 安全加固悄悄废掉了数学能力

- **现象**：为防代码执行加固 `calculate`（弃用 `eval`）之后，多步数学用例开始失败。
- **根因**：模型正确构造了 `sum(range(1, 101))`，但 AST 白名单没有放行 `sum` 与 `range`，
  直接拒绝求值。
- **解决**：白名单放行 `sum` / `range`，并对 `range` 长度设上限防止内存炸弹。
- **教训**：安全加固必须跑全量评测——没有评测闭环，这次"安全提升"会伴随能力回归
  且长期无人发现。

### 1.3 `^` 被当成异或

- **现象**：`2^10` 之类的乘方计算失败。
- **根因**：`^` 在 Python 里是异或不是幂，模型生成的表达式语义不符。
- **解决**：AST 白名单显式支持 `**`，评测集补充乘方用例。

### 1.4 模型心算不可靠

- **现象**：`1TB 等于多少 GB` 这类题模型直接心算作答，结果偶尔错误且过程不可审计。
- **根因**：system prompt 没有强制数值类问题走计算工具。
- **解决**：强化 prompt——所有数值类问题必须调用 `calculate`；评测集补多步计算类别，
  工具调用准确率升至 100%。同时引入新回归：模型解释拒绝原因时**举例输出了敏感文件
  格式**，再补输出约束修复。

### 1.5 rerank 阈值拍脑袋误杀正确答案

- **现象**："检索不到明明在文档里的内容"。
- **根因**：`RAG_MIN_SCORE=0.05` 是凭感觉定的，把相关度 0.0055 的正确答案过滤掉了。
- **解决**：实测分数分布——相关查询最高 0.97/0.93/0.0055，不相关 0.0000~0.0004，
  据此把阈值标定为 0.002，留 5 倍安全边际。

### 1.6 语义缓存阈值：命中率与误命中的两难

- **现象**：只按向量相似度判定时，「本金 5000 元 / 3.5%」与「10000 元 / 5%」相似度
  高达 0.9252 但答案完全不同（175 元 vs 500 元）；为防误命中把阈值提到 0.95，
  同义改写覆盖率却跌到 17%，缓存形同虚设。
- **解决**：增加"数字集合必须一致"的签名闸门（一行正则），最大误命中相似度降至
  0.8763，阈值得以回落到 0.92，覆盖率回到 50%，误命中保持 0。最终形成四道闸：
  相似度阈值 + 数字签名 + 能力签名（prompt/工具变更即失效）+ 上下文指纹。

### 1.7 安全红线过强，把知识库问题也拦了（公网部署后发现）

- **现象**：公网上问"会话保存在哪里？"，模型回答"涉及敏感信息，不能检索"——
  而这些内容正是知识库文档里公开收录的项目说明。
- **根因**：防提示注入的安全红线（"凡涉及系统配置不得检索"）措辞过宽，
  压过了知识库检索指引。
- **解决**：在 RAG 指引开头补充边界说明——红线针对的是**运行环境的真实敏感数据**
  （环境变量值、密钥、凭据），知识库收录的公开文档内容属正常使用场景。
- **教训**：与 1.2 同属"安全与能力的边界问题"——安全 prompt 的每一次收紧都需要
  用正常用例验证不误伤。

### 1.8 多轮会话延续拒绝模式

- **现象**：1.7 修复部署后，同一个会话里继续提问，模型依然拒绝。
- **根因**：多轮上下文里模型看到自己此前连续拒绝的历史，延续该行为模式——
  这是 LLM 会话的上下文惯性，不是服务端问题。
- **解决**：新建会话即恢复正常。诊断时"换新会话"应作为排查 LLM 行为问题的标准步骤。

### 1.9 评测 judge 服务商切换后报 400

- **现象**：LLM-as-judge 评测突然整批报 400。
- **根因**：切换了主模型服务商，但 judge 的模型名与端点配置没有跟着走。
- **解决**：judge 统一走 `LLM_*` 配置，与主模型共用一份服务商定义。

### 1.10 知识库为空时也挂载检索工具

- **现象**：空库状态下模型每轮都尝试调用必然失败的检索工具。
- **解决**：知识库为空时不挂载 `search_knowledge_base`（可用性在构建 Agent 时判定），
  空库不增加无效工具调用轮次。

## 二、RAG 检索链路

### 2.1 Markdown 表格被分块切散

- **现象**：问"会话保存多久"只召回到表格的后半段，1800 秒那一行在另一块，
  模型拼不出完整答案。
- **根因**：长段落超过 `chunk_size` 后按 `\n` 硬切，Markdown 表格从中间断开，
  表头与数据行分离。
- **解决**：分块器把表格视为**不可分割的原子单元**；CSV 转成 Markdown 表格
  也是为了保持这个属性。
- **附带发现**：overlap 会把前一块尾部拼到表格块开头，破坏"整块是一张表"的属性，
  单测锁死（答案可能照样对，但引用展示被污染——端到端评测极难发现的 bug）。

### 2.2 引用来源显示成随机 UUID

- **现象**：回答的引用来源显示 `d49f2c07...txt`，无法核验。
- **根因**：上传文件落地时按安全要求用随机 UUID 命名，这个磁盘名一路传到了前端展示。
- **解决**：入库时用原始文件名覆盖 chunk 的 `source` 元数据。

### 2.3 外部重建知识库后，服务永久写不进去

- **现象**：在另一个进程执行 `ingest --rebuild` 后，服务端每次写向量库都报
  `Collection [...] does not exist`，且不会自愈。
- **根因**：服务进程缓存了 Chroma 的集合句柄，外部重建后句柄指向已删除的集合。
- **解决**：捕获该错误后重新获取句柄并重试一次，而不是要求"重建后必须重启服务"。

### 2.4 镜像里没有 docs/ 目录

- **现象**：容器内执行 `ingest ./docs` 因目录不存在失败。
- **解决**：Dockerfile 补 `COPY docs/ ./docs/`；目录路径写错时也改为给出友好提示
  而非 traceback。

### 2.5 知识库为空时检索工具未挂载（启动时序）

- **现象**：ingest 灌库后提问，模型回答"没有相关信息"——检索工具压根没挂载。
- **根因**：工具挂载在 Agent 构建时一次性判定（`is_ready()`），backend 启动时
  知识库还是空的，之后灌库不会自动补挂载。
- **解决**：灌库后重启 backend。运维上"先灌库、再启动"是正确顺序。

## 三、多模态

### 3.1 主模型不支持图片

- **现象**：把图片塞给主模型（DeepSeek 纯文本）直接报错。
- **解决**：视觉模型（Qwen3-VL-32B）独立封装为 `analyze_image` **工具**而非旁路——
  看图结果进入推理链，可以与 `calculate` 组合（"图里 4 个方块，每个 5 元"→ 20 元）。

### 3.2 公开图片 URL 被模型服务商拒绝

- **现象**：传图片 URL 让服务商代下，直接被拒：
  `The image URL must be a valid and downloadable URL or look like data:...`。
- **解决**：服务端读出文件字节 base64 内联传输。副作用是图片体积直接换算 token 成本，
  所以图片上传上限（10MB）比普通文档（20MB）严格。

## 四、后端工程

### 4.1 ContextVar 不穿透线程池

- **现象**：访问日志里的 user 永远是 `-`。
- **根因**：`get_current_user` 是同步依赖，FastAPI 把它放进线程池执行——在那里修改
  ContextVar 不会传回外层协程，request_id 上下文断裂。
- **解决**：改为 `async def`，上下文正常穿透。

### 4.2 BaseHTTPMiddleware 对 SSE 长连接的缓冲风险

- **根因**：`BaseHTTPMiddleware` 会包装响应流，对 SSE 这类长连接有缓冲隐患。
- **解决**：改用裸 ASGI 中间件实现日志与 request_id 注入。

### 4.3 MCP SDK 2.x 改名

- **现象**：升级 mcp SDK 到 2.x 后 `from mcp.server.fastmcp import FastMCP` 直接 ImportError。
- **解决**：按版本取别名（try 2.x 的 `MCPServer`，fallback 旧路径），不锁死旧大版本。

### 4.4 Alembic 迁移与启动建表打架

- **现象**：`alembic upgrade head` 在建表前被启动代码的 `create_all` 抢先打断。
- **解决**：迁移期间 schema 所有权归 Alembic（env.py 强制 `DB_AUTO_CREATE=0`）；
  启动补丁对"表还不存在"的全新库安静跳过。

### 4.5 MySQL 迁移踩坑合集（SQLite → MySQL 8）

| 问题 | 根因与解决 |
| --- | --- |
| `VARCHAR requires a length` | SQLite 忽略 String 长度，MySQL 必须显式——模型与迁移文件全部补长度 |
| `connect_args` 报错 | `check_same_thread` 是 SQLite 专用参数，按方言条件化 |
| 空闲后连接失效 | MySQL `wait_timeout` 掐断连接，加 `pool_pre_ping` + `pool_recycle=3600` |
| 补列检查报错 | `PRAGMA table_info` 是 SQLite 专用，改 `information_schema` 跨方言实现 |
| 新库没有账号 | 注册开关已关，用 bcrypt 生成哈希直接 INSERT 管理员账号 |
| 迁移期间建表冲突 | 同 4.4，Alembic 独占 schema 所有权 |

### 4.6 alembic.ini 中文注释导致命令直接崩

- **现象**：Windows 上执行任何 alembic 命令报 `UnicodeDecodeError: 'gbk' codec`。
- **根因**：configparser 按 Windows 本地编码（GBK）读 ini，文件里的中文注释解码失败。
- **解决**：alembic.ini 改为纯 ASCII，中文说明挪到迁移文件的 docstring 里。

### 4.7 限流与降级

- **设计取舍**：Redis+Lua 滑动窗口保证多副本共享额度；Redis 挂了退化为进程内计数——
  限流不准好过服务不可用。熔断只计瞬时错误（401/内容拒绝不计入，否则一次用户
  输错就熔断），重试加抖动（无抖动则一批请求同时重试形成新尖峰）。

## 五、部署与运维（腾讯云轻量服务器）

### 5.1 服务器目录不是 git 仓库

- **现象**：`git pull` 报 `not a git repository`。
- **根因**：当初目录是直接上传的，不是克隆的。
- **解决**：`git init` + `git remote add origin ...` + `git fetch` + `git reset --hard origin/main`
  ——未跟踪文件（.env、uploads、rag_store）全部保留，仅同步被跟踪代码。

### 5.2 国内服务器直连 GitHub 失败

- **现象**：`git fetch` 长时间无输出，最终 `Failed to connect to github.com port 443`。
- **根因**：国内云服务器直连 GitHub 不稳定。
- **解决**：remote 换镜像代理前缀（`gh-proxy.com`），并用
  `git config --global url."<代理>".insteadOf "https://github.com/"` 一劳永逸。

### 5.3 `docker compose restart` 不读取新 .env

- **现象**：改了 `.env`（JWT 密钥、ADMIN_USERS）后 restart，配置不生效。
- **根因**：`restart` 只是重启进程，环境变量是**容器创建时**注入的。
- **解决**：需要 `docker compose up -d` 重建容器。
- **教训**：env_file 的变更必须 recreate，restart 只对镜像内代码变化场景有效。

### 5.4 .env 配置粘连与重复定义

- **现象**：`ADMIN_USERS` 不生效、JWT 密钥丢失。
- **根因**：脚本追加配置时缺换行，`ADMIN_USERS=demo,111` 与 `JWT_SECRET=...` 粘成一行；
  且文件里 `ADMIN_USERS` 定义了两次——dotenv 后者覆盖前者。
- **解决**：手工拆行、去重；追加配置的脚本一律带换行符。

### 5.5 新 MySQL 库里表建不出来 / 迁移报错

- 见 4.5；另注意首次部署顺序：`up -d --build` 等 mysql healthy → Alembic/自动建表 →
  再灌业务数据。

### 5.6 构建奇慢（3Mbps 带宽）

- **现象**：apt 一层 90 秒+，pip 依赖十几分钟，mysql 镜像 600MB 遥遥无期。
- **解决**：三层加速——
  1. Dockerfile 里 apt 换阿里云源、pip 换清华源；
  2. Docker 配置 `registry-mirrors` 指向腾讯云内网源 `mirror.ccs.tencentyun.com`
     （mysql 镜像走内网，速度与公网带宽无关）；
  3. `git fetch` 走镜像代理。
  构建总时长从预估 40+ 分钟降到 5 分钟内。

### 5.7 知识库灌库后模型仍说"没有相关信息"

- **现象**：ingest 成功（60 chunks），提问业务问题模型却不调用检索。
- **根因**：两个叠加——① 检索工具挂载是启动时判定（见 2.5）；② 多轮会话里模型
  延续此前的拒绝模式（见 1.8）。
- **解决**：重启 backend + 换新会话提问，检索与引用恢复正常。

### 5.8 公网暴露面收敛

- **措施**：Redis/MySQL 只走容器网络（`expose` 不写 `ports`）；backend 只绑
  `127.0.0.1:8000` 由前端 nginx 反代；注册开关 `REGISTER_ENABLED=0`（先建号后关闭）；
  防火墙只放行 80/8081；所有密钥经 `.env` 注入不入仓库。

## 六、前端与可观测性

### 6.1 CI 抓到的真实问题

- `api.js` 中 GET 请求仍传 `body` 字段——CI 的 lint+构建检查直接拦截。

### 6.2 看板趋势线把同一数据点画两次

- **现象**：趋势图"改进幅度"失真。
- **根因**：`latest.json` / `ci_baseline.json` 是其它报告的别名拷贝，混进趋势线导致
  同一数据点重复渲染。
- **解决**：趋势只用真实运行产生的报告，"最新指标"卡片单独优先读 `latest.json`。

### 6.3 时间筛选为空时图表残留旧数据

- **解决**：渲染空状态提示，不再残留旧图。

## 方法论小结

复盘这些问题，重复出现的模式有四个：

1. **"看起来是模型不行"的问题，先怀疑测量与配置**（1.1、1.5）——
   评测配置错误、阈值拍脑袋，比模型本身的缺陷更常见。
2. **安全与能力是一条边界，不是单向开关**（1.2、1.7、2.5）——
   每次安全收紧都要用正常用例验证没有误伤；每次能力放开都要确认没有打开攻击面。
3. **多组件系统的时序决定行为**（2.3、2.5、4.4、5.3、5.7）——
   启动顺序、缓存句柄、环境变量注入时机，这些"什么时候发生"的问题比"怎么做"更隐蔽。
4. **LLM 的行为会被上下文塑形**（1.8、5.7）——
   排查 LLM 异常行为时，"换一个新会话"应作为第一个排除项。
