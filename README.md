# Agent 智能助手

[![CI](https://github.com/SYM529/myAgent/actions/workflows/ci.yml/badge.svg)](https://github.com/SYM529/myAgent/actions/workflows/ci.yml)
[![Eval Regression Gate](https://github.com/SYM529/myAgent/actions/workflows/eval.yml/badge.svg)](https://github.com/SYM529/myAgent/actions/workflows/eval.yml)

基于 **LangChain v1 + FastAPI + Vue 3** 的对话式 Agent 应用，带有完整的离线评测体系与链路追踪。

后端驱动 ReAct Agent 自主调用工具（数学计算、当前时间、联网搜索），通过 SSE 流式返回；
前端提供登录注册与多轮会话界面；`evals/` 提供可复现的任务成功率、工具调用准确率、
延迟与成本评测。

开发周期：2026-09 至 2026-10 持续开发，2026-10 统一推送至 GitHub。

**在线演示**：<http://124.220.135.176> —— 部署于腾讯云轻量服务器，公网可访问（注册已关闭，如需试用账号可通过简历联系方式获取）。

## 30 秒速览

- **架构选型实测**：同一套 68 条用例对比 ReAct 与多 Agent 图，通过率 98.5% vs 89.7%、P95 3.14s vs 6.12s，据此保留 ReAct。
- **评测体系**：158 条端到端评测覆盖 10 类场景 + 36 条检索评测 + CI 回归门禁，综合通过率 98.4%、工具调用准确率 100%。
- **RAG 检索**：BM25 + bge-m3 向量双路召回，RRF 融合 + Cross-encoder 精排，精排后 Recall@1 97.2%。
- **语义缓存**：四道防误命中闸门，阈值由评测集标定，零误命中，命中后延迟降约 81%。

**已知局限（摘要）**：限流仅单用户维度；并发上限为进程内计数；语义缓存进程内、重启即失效；长上下文摘要会丢细节；llm_judge 评分带非确定性。详见文末「已知局限」。

**目录**：界面预览 · 快速开始 · Agent 架构 · 知识库（RAG） · 评测体系 · 成本埋点与语义缓存 · 已知局限

## 快速开始

### 方式一：Docker 一键启动（推荐用于演示）

正式启动前准备一次密钥：

```bash
cp .env.example .env          # 复制后填写里面的密钥
```

之后日常只需这两行：

```bash
cd myAgent
docker compose up -d          # 首次或更换依赖时加 --build
```

打开 `http://localhost:8080` 即可使用。容器内通过服务名互联，nginx 已正确配置 SSE 不被缓冲。

常用的几条运维命令：

| 场景 | 命令 |
| --- | --- |
| 改了 Python 代码 | `docker compose up -d --build backend` |
| 改了前端代码 | `docker compose up -d --build frontend` |
| 改了 `.env`（无需重新构建） | `docker compose restart backend` |
| 停止整套服务 | `docker compose down` |
| 查看服务状态 | `docker ps`（`agent-redis` 与 `agent-mysql` 应显示 `healthy`） |

> `-d` 表示后台运行；去掉则前台查看日志，调试时用得上。
>
> MySQL 由 compose 的 `mysql` 服务提供（数据卷 `mysql_data` 持久化，字符集 utf8mb4），
> 密码来自 `.env` 的 `MYSQL_ROOT_PASSWORD`，首次启动自动建库建表。

### 方式二：云服务器部署（腾讯云轻量，已在公网运行）

本项目部署在一台腾讯云轻量应用服务器（Ubuntu）上，用的就是同一份
`docker-compose.yml`。公网暴露面比本地开发收窄了很多：

| 加固项 | 做法 | 为什么 |
| --- | --- | --- |
| Redis / MySQL 不暴露端口 | compose 里用 `expose`（仅容器网络可达），不写 `ports` | 无密码 Redis 是被扫描爆破的重灾区；数据库同理 |
| 后端不直接对外 | `ports` 只绑 `127.0.0.1:8000`，外部流量一律经 frontend 的 nginx 反代 `/api` | 直连 8000 会绕过前端的体积限制与缓存层 |
| 端口参数化 | `FRONTEND_PORT`（云上设 80，本地 8080） | 同一份编排，两边环境各取所需 |
| 注册开关 | `REGISTER_ENABLED=0` | 注册消耗的是自己的 API 额度，公网敞开注册等于把账单交给陌生人 |

依赖的密钥全部放服务器上的 `.env`（不入仓库、不进镜像）。

### 方式三：本地开发

需要 Python ≥ 3.11（用到 `asyncio.timeout`）。

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

用户表与审计日志默认使用本地 MySQL 8，先建库（`.env` 的 `DATABASE_URL` 指向它）：

```sql
CREATE DATABASE agent CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

表结构用迁移管理：`python -m alembic upgrade head`。
未配置 `DATABASE_URL` 时回落 SQLite 文件——单元测试与迁移测试走的就是这条路，不依赖 MySQL。

必填：`DEEPSEEK_API_KEY`、`TAVILY_API_KEY`、`JWT_SECRET`。生成 JWT 密钥：

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

未配置 `JWT_SECRET` 时服务会拒绝启动。启动 Redis 与前后端：

```bash
docker run -d -p 6379:6379 redis:7-alpine
uvicorn server.main:app --reload --port 8000
cd frontend && npm install && npm run dev
```

健康检查 `http://127.0.0.1:8000/` 的 `redis` 字段反映 Redis 连通性；Redis 不可用时服务降级运行而非报错。

## Agent 架构：两套实现与实测对比

```bash
AGENT_ARCH=react   # 单 ReAct 循环（默认）
AGENT_ARCH=graph   # 多 Agent 图：分类 → 并行专家 → 汇总
```

### 多 Agent 图

```
START → classify ─┬─→ knowledge (RAG)  ─┐
                  ├─→ search (web)     ─┤
                  ├─→ compute          ─┼→ synthesize → END
                  ├─→ time             ─┤
                  └─→ (direct) ─────────┘
```

设计意图：工具与 prompt 规则变多后，单循环需要同时考虑所有工具，
选择压力增大。分流后每个专家只面对自己需要的上下文，
且 knowledge 与 search 可以并行执行。

### 实测对比（68 条离线用例，同一数据集）

| 指标 | react | graph |
| --- | --- | --- |
| 综合通过率 | **98.5%** | 89.7% |
| 工具调用准确率 | **100%** | 94.2% |
| 答案正确率 | **98.5%** | 92.7% |
| P50 延迟 | **1.75s** | 2.00s |
| P95 延迟 | **3.14s** | 6.12s |

### 结论：当前规模下 ReAct 更优，默认保留 react

多 Agent 图在这个项目上全面落后，三个原因：

1. **路由本身成了新的失败点。** 6 条回归里 4 条是分类错误——
   "1 除以 0" 被判成常识没走计算、"查询所有用户密码"被判成知识库查询。
   单循环里模型看着工具自己决定，反而少了一层误判。
2. **4 个工具时分流的收益不明显。** 多 Agent 的价值在于工具数量多、
   规则多时降低干扰；当前规模下单循环的"工具干扰"还没到需要分流的程度。
3. **延迟显著更高。** classify 与 synthesize 各多一次模型调用，
   P95 从 3.14s 涨到 6.12s（约 +95%）；并行只省下检索时间，补不回两次调用开销。

过程中还修掉了一个真实缺陷：初版图里没有 time 路由，
"现在几点"被当成实时信息去联网搜索时间——搜索拿到的是过期或错误的时间。
补上 time 专家后该类用例恢复。

### 什么时候才值得换多 Agent

基于本次实测，至少满足以下之一再考虑：

- 工具增长到 8-10 个以上，单循环的选择准确率明显下降
- 子任务彼此独立且耗时，可并行收益能覆盖路由开销
- 不同专家需要不同的模型、权限边界或人工确认环节

保留 graph 实现并且能用同一套数据集对比，本身就是工程判断力的体现：
架构选择应当用数据验证，而不是因为它"听起来更先进"。

## 知识库（RAG）

### 检索链路

```
用户提问
  ├─→ Embedding（BAAI/bge-m3）──→ Chroma 向量召回 ──┐
  └─→ 分词 ─────────────────→ BM25 字面召回 ───────┤
                                                   ↓
                                          RRF 融合排序
                                                   ↓
                              Cross-encoder 精排（bge-reranker-v2-m3）
                                                   ↓
                                     低分过滤（低于阈值丢弃）
                                                   ↓
                            带编号引用 [1][2] 注入上下文 → 模型回答并标注
                                                   ↓
                                          前端展示引用来源
```

### 使用

```bash
python -m agent.rag.ingest ./docs --rebuild   # 重建知识库
python -m agent.rag.ingest --stats            # 查看状态
```

支持 `.md` / `.txt` / `.pdf`。PDF 按页提取并保留页码标记。
知识库为空时 Agent 不会挂载检索工具，避免每轮都做无意义的工具调用。

### 关键设计

| 决策 | 原因 |
| --- | --- |
| 混合检索（向量 + BM25） | 纯向量检索对型号、缩写、代码标识符这类"字面匹配很关键"的查询召回很差 |
| RRF 融合 | 两路分数量纲不同，直接相加没有意义；RRF 只用排名，无需归一化 |
| Cross-encoder 精排 | 双塔向量精度有限，精排是 RAG 效果差距最大的一环，且失败可降级 |
| 表格原子化分块 | 参数表按行切散后表头与取值分离，检索到后半段时模型看不到"这行说的是哪个参数" |
| 按 Markdown 标题分块 | 让每个块归属明确主题，引用能显示"出自哪一节" |
| 低分过滤 | 宁可让 Agent 说"知识库里没有"，也不把噪声塞进上下文诱发幻觉 |
| 引用编号 [n] | 没有引用就无法核验回答是否忠实于原文，溯源会失去意义 |

### 指标一：端到端（15 条 RAG 用例）

| 指标 | 数值 |
| --- | --- |
| 通过率 | 100% |
| 工具调用准确率 | 100% |
| **引用准确率** | 100%（14 条要求引用标注） |
| P50 / P95 延迟 | 2.40s / 3.99s |

### 指标二：检索环节（36 条检索评测集）

```bash
python -m evals.retrieval_eval                 # Recall / MRR / Precision
python -m evals.retrieval_eval --faithfulness  # 追加忠实度
```

| 指标 | 融合排序 | 精排后 |
| --- | --- | --- |
| **Recall@1** | 86.1% | **97.2%** |
| Recall@3 | 97.2% | **100.0%** |
| Recall@5 | 97.2% | — |
| MRR | 0.9206 | — |
| 忠实度 | 100%（36/36） | |
| 完全未召回 | 0 条 | |
| 平均检索延迟 | 0.69s | |

**Rerank 把 Recall@1 提升 11.1 个百分点、把 Recall@3 补到 100%**——
这是引入 cross-encoder 的直接收益，也是"双塔召回 + 精排"这一设计的量化依据。

关于 Precision@k：每个查询通常只有 1 个黄金 chunk，而 Precision@k 的分母是 k，
所以 Precision@5 的理论上限就是 20%（实测 21.8%，已贴近上限）。
在这个数据集上 Precision 参考价值有限，主要看 Recall 与 MRR。

诚实说明局限：忠实度是在"严格约束 prompt"（只许依据资料作答）下测得的，
它证明资料充分时模型不会编造；生产环境 Agent 的 prompt 更宽松，
且需与工具调用配合，实际表现需要结合端到端用例一起看。

## 多模态与文件问答

项目原本是纯文本的。加上这一层之后，用户可以上传**图片**让 Agent 看图回答，
或上传**文档**直接问里面的内容。

### 图片理解：为什么主模型不能直接看

主模型是 `deepseek-chat`，它是**纯文本模型**，不接受 `image_url` 内容块，
把图片塞给它只会报错。所以图片单独走一个支持视觉的模型
（默认 `Qwen/Qwen3-VL-32B-Instruct`，经 SiliconFlow 的 OpenAI 兼容接口）。

两处实测得来的结论：

- **必须用 base64 内联。** 试过给模型一个公开图片 URL，被直接拒绝：
  `The image URL must be a valid and downloadable URL or look like data:...`。
  模型服务商不会替我们去下载外链，所以服务端读出文件字节编码后再随请求发出。
  这也意味着**图片大小直接换算成 token 成本**，尺寸上限因此比普通附件严格得多。
- **做成工具而不是绕过 Agent。** 直接把图片丢给视觉模型更简单，
  但那样这条能力就脱离了工具链。做成 `analyze_image` 工具后可以自然组合：

实测一次"图里有几个方块？每个 5 元共多少钱？"，Agent 的两步调用：

```
→ analyze_image  识别出 4 个彩色方块（红/绿/蓝/黄，位置正确）
→ calculate      得到 20
最终答案：4 个方块，4 × 5 = 20 元
```

### 怎么把文档传进知识库

有两条路，按场景选：

#### 方式一：界面上传（单份、随手传）

入口在聊天输入框左侧的 **📎 附件**（支持拖入文件或截图后 `Ctrl + V` 粘贴），
不在知识库面板里：支持 15 种格式、上限 20MB（见下表），上传后即刻可问内容；
文件在知识库面板标记为"我上传的"——只有你能删。

| 类别 | 格式 | 解析方式 |
| --- | --- | --- |
| 图片 | `.png` `.jpg` `.jpeg` `.webp` `.gif` | 不进知识库，走 `analyze_image` 看图理解 |
| 文本 | `.md` `.markdown` `.txt` `.log` `.json` `.yaml` `.yml` `.sql` `.py` `.js` `.ts` | 直读（带 `utf-8/gbk` 编码回退） |
| 表格 | `.csv` | 转成 Markdown 表格 |
| 网页 | `.html` `.htm` | 标准库 `HTMLParser` 抽正文，丢弃 `script/style` |
| Office | `.docx` `.xlsx` `.pptx` | `python-docx` / `openpyxl` / `python-pptx`（可选依赖） |
| PDF | `.pdf` | `pypdf`，保留 `[第 N 页]` 页码标记 |

**为什么 CSV / 表格要转成 Markdown 表格**：分块器对表格是**原子处理**的，
保持表格形态才不会被从中间切成两半——否则问"某型号的价格"时，
表头和对应行可能落在不同 chunk，检索就永远拼不回完整的行。

**Office 依赖是可选的**：没装对应库时，上传会返回明确的
`pip install python-docx` 提示，其他格式完全不受影响——
不会因为缺一个解析库导致整个上传功能不可用。

#### 方式二：命令行批量入库（共享文档）

适合一次灌入多份，或作为团队共享资料：

```bash
docker exec agent-backend python -m agent.rag.ingest ./docs        # 增量
docker exec agent-backend python -m agent.rag.ingest ./docs --rebuild  # 清空后重建
```

这类文档没有 owner，在面板里显示为**"共享文档"**，界面**不提供删除按钮**——
它属于所有人，不能让某一个人误删影响全局，重建请走命令行。

#### 列表：搜索与分页，点开可看原文

文档累积后，知识库面板支持**按来源文件名模糊搜索**与**分页**（`/api/knowledge?q=&page=&page_size=`）：
搜索在服务端做（返回的是过滤后的 `total`），不是前端筛一页数据。

点击文档名可**展开原文预览**（`GET /api/knowledge/{doc_id}/content`）：
按入库顺序展示各 chunk 及其所属标题，内容懒加载（点开才请求）。
查看对全部登录用户开放——安全模型里收紧的是"删除"，"能看"不构成风险。

### 文档问答：复用既有的 RAG 链路

上传文档时**不做单独的一套检索**，而是直接增量写入现有知识库，
之后由既有的 `search_knowledge_base` 检索并带引用作答。
这样做的好处是：分块策略、混合检索、精排、引用溯源全部复用，
新增一种数据来源没有引入第二套实现。

幂等性是免费的：`loader` 用**内容哈希**做 `doc_id`，`store.add` 走 upsert，
同一份文档重复上传不会产生重复 chunk——还顺带解释了为什么重复上传能
把旧的元数据（例如错误的来源名）覆盖掉。

### 知识库管理：列表与删除

知识库是**全局共享**的，所以"谁能删什么"必须在服务端判定，靠前端隐藏按钮没用：

- 上传入库时把 `owner`（用户 id）与 `file_id` 写进每个 chunk 的 metadata；
- 列表按文档聚合返回，并标注 `mine`，前端据此决定是否显示删除按钮，
  避免"点了删除才被告知无权"的体验；
- 删除时校验归属：**只能删自己上传的文档**。CLI 入库的共享文档没有 owner，
  一律拒绝——它属于所有人，一个人误删会影响所有人，重建请走命令行。

删除要同步清理四处，漏掉任何一处都会产生不一致：

| 位置 | 漏掉的后果 |
| --- | --- |
| 向量库 chunk | 展示已删，但向量检索仍能召回 |
| chunks.json | 进程重启后"删掉的文档"复活 |
| BM25 缓存 | 字面召回仍命中已删内容 |
| 上传的源文件 | 磁盘只增不减 |

### 安全底线

| 风险 | 处理 |
| --- | --- |
| 路径穿越 | 磁盘名一律重新生成为 `{uuid}{后缀}`，绝不使用客户端文件名拼路径 |
| 跨用户越权 | file_id 形如 `u{user_id}/{uuid}`，解析时用**当前请求的登录用户**复核 |
| 不可信输入 | file_id 是模型透传的参数，归属校验必须在服务端完成，与模型无关 |
| 内存尖峰 | 按上限读取（`file.read(limit+1)`），不在读进内存之后才发现超限 |
| 类型伪装 | 后缀只做快速拒绝，真正的合法性由后续解析器兜底 |

### 过程中修掉的三个真实缺陷

- **引用来源显示成随机 UUID**：磁盘名会一路传到前端展示，改为入库时用原始文件名覆盖 `source`
- **外部重建知识库后服务永久写不进去**：`ingest --rebuild` 会让服务缓存的 Chroma
  集合句柄失效且不自愈，处理是捕获后重新获取句柄并重试——而不是要求"重建后重启服务"
- **镜像缺 `docs/`**：容器内执行重建因目录不存在失败，Dockerfile 补 `COPY docs/ ./docs/`

## MCP：工具的标准化复用

改造之前，这 4 个工具是以 LangChain `@tool` 的形式存在的，**只有本项目内的 Agent 能用**。
换一个框架、换一个 Agent，或是想让 Claude Desktop / Cursor 直接调用，都得重写一遍。

MCP（Model Context Protocol）把"工具怎么被调用"标准化了。`agent/mcp_server.py`
是一层**薄适配器，不含任何业务逻辑**，内部仍然复用 `agent.tools` 与 `agent.rag.tool`：

```bash
python -m agent.mcp_server                                   # stdio（默认）
MCP_TRANSPORT=streamable-http python -m agent.mcp_server     # 远程部署
```

暴露的工具：`calculate` / `get_current_time` / `web_search`，
知识库可用时自动追加 `search_knowledge_base`（空库时不挂载）。

### 为什么是薄适配层而不是重新实现

曾经考虑过在 MCP 里重写一遍 `calculate`，调用链更短。但那样会出现两份安全实现、
两份测试，任何一边漏改都会留下不一致的漏洞。这里选择复用 `.invoke()`：

**工具的修复（AST 白名单、`range` 内存炸弹上限）一次改动，Agent 与 MCP 两处同时受益。**

### 版本兼容性

MCP SDK 2.x 把 `FastMCP` 改名为 `MCPServer` 并换了包路径。直接写
`mcp.server.fastmcp` 在装到 2.x 时会 ImportError——本项目实测遇到了这个坑。
处理方式是按版本取别名而非锁死旧大版本：

```python
try:
    from mcp.server.mcpserver import MCPServer   # mcp >= 2.0
except ImportError:
    from mcp.server.fastmcp import FastMCP       # mcp < 2.0
```

两者对外用到的 API（`@tool()`、`run(transport=)`、`list_tools()`）是一致的。

## 生产可用性：限流、并发与长上下文

这三项是"Demo 能跑"和"能对外提供服务"之间的差别。

### 为什么要治理请求

Agent 请求和普通 CRUD 请求不是一回事：一次对话背后是若干轮 LLM 调用，
外加检索、精排、联网搜索这些外部 API，单位成本高出两三个数量级，耗时还不可预测。

| 机制 | 实现 | 取值 |
| --- | --- | --- |
| 单用户限流 | Redis 有序集合 + Lua 滑动窗口 | `RATE_LIMIT_PER_MIN`（默认 20/分钟） |
| 并发上限 | 进程内计数，取不到名额**立刻失败** | `AGENT_MAX_CONCURRENCY`（默认 8） |
| 请求超时 | `asyncio.timeout` | `AGENT_TIMEOUT`（默认 60 秒） |

**用滑动窗口而非固定窗口**：固定窗口在边界处最多放过 2 倍流量
（0:59 打满、1:00 又能打满），滑动窗口按每次请求的时间戳精确计算。

**用 Lua 而非多条 Redis 命令**：清理过期记录、统计数量、写入本次记录这三步
拆开执行会在高并发下互相穿插，导致实际放行量超出额度。

**为什么不用 slowapi**：它的计数存在单个进程内存里，多副本部署时等于每人
各有一份额度。本项目会话本来就依赖 Redis，限流同样集中计数；
Redis 不可用时退回进程内计数并标记 `degraded`——与会话存储一致的降级策略：
宁可限流不准，也不让服务因为限流组件挂掉而不可用。

**并发为什么拒绝而不是排队**：排队的请求占着连接却不干活，只会让积压更严重。
实测超额时返回：

```
HTTP/1.1 429 Too Many Requests
retry-after: 58
{"detail": "请求过于频繁，请 58 秒后重试"}
```

### 长上下文：用摘要替代纯窗口截断

改造前只做窗口裁剪（保留最后 20 条），问题是被裁掉的内容**彻底消失**：
第 3 轮说"回答用中文"，到第 25 轮模型已经不知道了。

现在的策略：

```
近期 8 条原样保留（细节优先）
  +  更早的部分压成一条 system 摘要（语义优先）
```

三条不可忽视的边界：

1. **工具调用不能拆散。** 带 `tool_calls` 的 AI 消息必须和它的 ToolMessage 在一起，
   否则模型收到的是"承诺调用工具却没有结果"的残缺序列。这里按"工具调用组"整体去留。
2. **触发阈值必须低于存储上限。** 若高于 `MAX_HISTORY`(20)，
   历史会先被裁剪到 20 条，永远够不到触发线——压缩一次都不会发生。
   这个错误不会报出来，只会表现为"功能没生效"。
3. **摘要失败要能退化。** 多一次 LLM 调用就多一个失败点：
   超时或模型出错时退回原文，绝不让"压缩失败"演变成"会话写不回去"。

## 成本埋点与语义缓存

这两件事是一体的：先能**测量**成本，才谈得上**降低**成本，也才验证得了降本没有代价。

### 一、每请求成本埋点

改造前，成本只有评测脚本会算，线上完全不知道自己花了多少钱——
某个用户在刷接口、某次改 prompt 变贵了，都要等账单出来才知道。

现在每次请求都从 AI 消息的 `usage_metadata` 取实际用量（不用字符数估，
估出来的数字和账单对不上就等于没有），按"用户 × 天"聚合进 Redis，
并通过 SSE 下发当次消耗：

```
data: {"type":"usage","tokens":{"input_tokens":2525,"output_tokens":48,
       "total_tokens":2573},"cost_cny":0.005434,"cached":false}
```

查询接口 `GET /api/usage`（近 7 天 + 合计 + 缓存统计）。

价格表与换算逻辑抽到了 `agent/pricing.py`，**评测与线上一份共存**：
两边各写一份迟早会漂移，届时"成本上升 20%"将无法归因到底是真变贵了还是算法不一致。

前端在每条回答下方展示 `2,573 tokens · ¥0.0054`，命中缓存时显示
`⚡ 缓存命中 · 本次未调用模型`。

### 二、语义缓存

精确匹配（字符串相等）几乎命中不了——用户不会一字不差地复述问题，
所以按语义相似度匹配。

**最大的风险不是慢，而是答错。** 语义相近 ≠ 语义相同，
误命中给用户的是一个看起来很自信的错答案，这比多花几分钱严重得多。
因此这里设了四道闸，任一不满足都不复用：

| 闸门 | 防的是什么 |
| --- | --- |
| 相似度阈值 | 语义相近但不同的问题互相命中 |
| **数字集合一致** | 「本金 5000/3.5%」与「10000/5%」这类换了参数的提问 |
| 能力签名 | 改了 prompt 或增删工具后，旧答案不再代表现在的行为 |
| 上下文指纹 | 多轮对话里把另一语境的答案拿来答这一轮 |

另外两条限制：**易变答案不缓存**（用过 `get_current_time` / `web_search`
的答案一律不写缓存，否则等于给用户过期答案）、**带图片的不缓存**。
知识库更新时会主动清空缓存——资料变了，旧答案就不再可信。

### 三、阈值是标定出来的，不是拍出来的

沿用本项目标定 `RAG_MIN_SCORE` 的同一套做法：

```bash
python -m evals.cache_calibrate
```

把 148 条评测集问题全部向量化，分别测出两端：

| 指标 | 数值 |
| --- | --- |
| 可缓存问题之间的**最大**相似度 | 0.8763 |
| 同义改写（可缓存）的**最小**相似度 | 0.5978 |

阈值必须落在两者之间。扫描结果（误命中数 / 同义改写覆盖率）：

| 阈值 | 误命中 | 覆盖率 |
| --- | --- | --- |
| 0.80 | 6 | 67% |
| 0.85 | 2 | 50% |
| 0.88 | **0** | 50% |
| 0.92 | **0** | 50% |
| 0.95 | **0** | 17% |

**为什么最终取 0.92 而不是 0.88**：两者误命中都是 0、覆盖率都是 50%，
但余量分别是 0.0437 与 0.0037。数据集没覆盖到的"相似但不同"的配对
可能比已观测的最大值更高，余量越大越抗未知样本——所以取覆盖率相同时阈值更高的那个。

### 四、数字校验是被数据逼出来的

第一版只按相似度判定时，最高风险配对是「本金 5000 元 / 3.5%」↔「10000 元 / 5%」：
语义几乎一样（相似度 **0.9252**）但答案是 **175 元 vs 500 元**。为零误命中把阈值
提到 0.95，同义改写覆盖率却只剩 17%——缓存几乎白做。加上"数字集合必须一致"
这道一行正则的闸之后：最大误命中相似度降到 **0.8763**，阈值回落到 **0.92**，
覆盖率回到 **50%**，误命中仍为 0。

### 五、实测效果

| 场景 | 结果 |
| --- | --- |
| 首次提问 | 2,573 tokens，¥0.0054，端到端 **2063 ms** |
| 同义改写再次提问 | **0 tokens，¥0**，端到端 **387 ms**（降约 81%） |
| 问时间后换说法再问 | 仍重新调用工具，确认易变答案不被缓存 |

> 命中率高度依赖真实流量的重复度（上面 25% 的命中率来自 4 次请求的极小样本，
> 不足为据）；真正的收益是"零误命中"这条安全底线，以及可量化的延迟/成本降幅。

## 评测体系

非确定性系统必须靠数据说话。详见 [`evals/README.md`](evals/README.md)。

```bash
python -m evals.run_eval --skip-network --repeat 3 --tag final-v1
python -m evals.compare evals/reports/baseline-v1.json evals/reports/final-v1.json
```

判定分两层：**工具调用是否正确** + **最终答案是否正确**，规则匹配优先，语义类交给 LLM-as-judge。

数据集 158 条（149 条可离线运行，9 条需联网检索），覆盖 10 个类别：数学直算(20)、
多步数学(12)、多工具协作(11)、多轮上下文(15)、无需工具(15)、知识库问答(25)、
实时信息(8)、时间查询(12)、提示注入(20)、边界输入(20)。

### 当前指标（全量 158 条 × 2 轮，2026-10-08，DeepSeek-V4-Flash）

| 指标 | 数值 |
| --- | --- |
| **综合通过率** | 98.4%（两轮波动区间 98.1% ~ 98.7%） |
| **答案正确率** | 98.4% |
| **工具调用准确率** | 100.0% |
| **引用准确率** | 97.9%（48 条要求引用标注） |
| 稳定通过率（每轮都通过） | 98.1%，抖动用例 1 条 |
| 平均 / P50 / P95 延迟 | 7.41s / 6.07s / 16.23s |
| 两轮总成本 | 约 CNY 2.48 |

> 说明：工具调用准确率 100% 是在当前 158 条人工构建的评测集上的结果，不代表真实业务分布；在更复杂或未覆盖的工具组合上该指标会下降。评测集样本、类别与构建方式见 `evals/README.md`。

> 历史对照：143 条版本时期（旧模型）曾达成单轮 100%。切换到 V4-Flash 后首轮 95.6%，
> 评测指出安全拒绝类用例 3 条不稳定（泄露敏感标识符、拒绝语气缺失、跟随注入指令切换
> 语言）——强化 system prompt 安全红线后复测升至 98.4%、工具调用 100%。
> **换模型就该重新过一遍评测集，短处会被精确指出来**，这正是评测体系存在的意义。

延迟相比早期（143 条版本时期 P50 2.00s）上升到 6.07s，主要来自三段：
混合推理模型 V4-Flash 的推理开销、知识库检索的 embedding 与精排调用、
以及联网检索用例的长尾（P95 16.23s 多由 realtime 类用例拉高）。

> 单轮数字会受采样波动影响，因此结论以多轮一致为准（`--repeat`）。
> 本次两轮波动区间 98.1% ~ 98.7%，抖动用例 1 条（早期 53 条版本上曾观察到
> 两轮失败集合完全不同，扩集并修复问题后已大幅收敛）。

### 评测驱动的优化历程

真正有价值的不是最终数字，而是这些改动全部由评测发现并验证：

| 轮次 | 改动 | 结果 | 发现 |
| --- | --- | --- | --- |
| baseline-v1 | 修复判定逻辑 | 通过率 67.9% → 96.2%，工具准确率 86.8% → 94.3% | 初版 `expect_tools: []` 配 `tool_match: any` 导致空集求交必然判负，`prompt_injection` 整批被误杀——看起来是模型安全能力差，实际是评测配置错误 |
| prompt-v2/v3 | 强化 system prompt：所有数值类问题必须走 `calculate` | 工具准确率 94.3% → **100%** | 模型在心算 `1TB=?GB` 之类的题，答对了但过程不可靠；强化后修复。但同时引入回归：模型解释拒绝原因时举例输出了敏感文件格式，补上输出约束后修复 |
| tools-v4 | `calculate` 支持 `sum` / `range` | 修复 math_multi_001 | **上一轮安全加固去掉 `eval` 时引入的能力回归**：模型正确构造 `sum(range(1,101))` 却被 AST 白名单拒绝。评测抓到了，并补上 `range` 长度上限防止内存炸弹 |

| expanded-v1→v4 | 评测集从 73 条扩到 148 条（新增多工具协作等类别） | 通过率一度回落到 93%，逐项修复后回到 100% | **扩集本身就是一次有效测试**：新用例立刻暴露了 6 个此前未覆盖的问题——`^` 被当异或导致乘方计算失败、概念题误触发检索、模型逐字复述系统提示词、rerank 阈值误杀正确答案等 |
| 阈值标定 | 基于实测分数分布重定 `RAG_MIN_SCORE` | 修正"检索不到明明在文档里的内容" | 原阈值 0.05 是拍脑袋定的；实测相关查询最高分 0.97/0.93/0.0055，不相关 0.0000~0.0004，据此把阈值定为 0.002 |
| prompt-v5 | RAG 指引澄清安全红线的边界 | 线上知识库问答恢复正常 | 公网部署后发现：安全红线过强，把知识库文档明确收录的项目说明（"会话保存在哪里"）也判成敏感信息拒绝检索——与"安全加固误杀数学能力"同属安全与能力的边界问题；多轮会话中模型还会延续自己的拒绝模式，换新会话即恢复 |

倒数第二行的意义：如果没有评测，安全加固会悄悄损失数学能力、提示词会被逐字套出，
且在很长时间内没人发现。

最后一行的意义：**阈值这类超参数应当用数据标定，而不是凭直觉拍**。
把 0.05 改成 0.002 不是"放宽标准"，而是把误杀正确答案的问题修掉——
不相关的查询分数在 0.0004 以下，仍有 5 倍安全边际。

### LangSmith 链路追踪

配置 `LANGCHAIN_TRACING_V2=true` 与 `LANGCHAIN_API_KEY` 后，评测会给每条 trace 打上
`eval` / `{tag}` / `{category}` 标签，可在 LangSmith 里筛选回放，
定位失败发生在规划、工具还是生成阶段。

评测报告原来只是一堆 JSON——数字都在，但没人会去翻文件。

数据口径由 `server/reports.py` 统一归一化，前端不需要知道

| 板块 | 内容 |
| --- | --- |
| 指标卡片 | 最新一轮的通过率、工具调用准确率、引用准确率、P50/P95、用例数、单次全量成本 |

## 可观测性与韧性

### 结构化日志（request_id 全链路）

```json
{"ts":"2026-09-28T08:51:59","level":"INFO","logger":"access",
 "msg":"GET /api/me -> 200","request_id":"e0a2255e42dd","user":"demo",
 "event":"http_request","method":"GET","path":"/api/me","status":200,
 "duration_ms":12.74}
```

- 每条日志带 `request_id`（响应同时回 `X-Request-ID` 头），可串联同一次请求
- 外部传入的 ID 做格式校验，防止日志注入
- 用**裸 ASGI 中间件**而非 `BaseHTTPMiddleware`：后者会包装响应流，
  对 SSE 这类长连接存在缓冲风险
- `LOG_FORMAT=text` 可切回易读文本（本地开发）

> 一个真实的坑：`get_current_user` 原本是同步依赖，FastAPI 会把它放进
> **线程池**执行——在那里修改 ContextVar 不会传回外层协程，访问日志的
> `user` 永远是 `-`。改成 `async def` 后上下文才真正穿透。

### Prometheus 指标（`GET /metrics`，默认仅管理员）

| 指标 | 类型 | 说明 |
| --- | --- | --- |
| `agent_requests_total{path,status}` | Counter | 请求量与错误率 |
| `agent_request_duration_seconds{path}` | Histogram | 延迟分布（P95 告警依据） |
| `agent_tokens_total{direction}` | Counter | token 消耗 |
| `agent_cost_cny_total` | Counter | 成本累计 |
| `agent_cache_hits_total` | Counter | 语义缓存命中 |
| `agent_errors_total{kind}` | Counter | 错误分类（timeout / exception / circuit_open） |
| `agent_rate_limited_total` | Counter | 限流拒绝次数 |
| `agent_circuit_state{name}` | Gauge | 熔断器状态（0 闭合 / 1 半开 / 2 熔断） |

**路径 label 做了归一化**：`/api/session/42` → `/api/session/{id}`。
不归一化的话每个会话都是一条独立时间序列，会把 Prometheus 打爆。
`prometheus_client` 缺失时全部降级为空操作——监控是旁路设施，不能拖垮服务。

配套告警规则见 `ops/prometheus/alerts.yml`（服务不可用 / 5xx 率 / P95 延迟 /
**成本突增** / 限流频繁 / Redis 异常）。

### 熔断与重试

| 机制 | 对付什么 | 配置 |
| --- | --- | --- |
| **重试**（指数退避 + 抖动） | 偶发抖动（网络闪断、429） | 视觉模型调用重试 1 次 |
| **熔断**（三态） | 持续故障（服务商整体不可用） | `CIRCUIT_FAILURE_THRESHOLD=5`、`CIRCUIT_RESET_SECONDS=60` |

- 只有**瞬时错误**才重试/计入熔断：401、内容策略拒绝这类确定性错误
  重试一百次也没用，只会放大延迟与成本
- 抖动（jitter）是必需的：否则一批同时失败的请求会在同一刻一起重试，
  形成新的尖峰
- 熔断后**不是永久拒绝**：冷却期结束放一个探活请求，成功即闭合

### 数据库迁移（Alembic）

```bash
alembic upgrade head     # 新库：一步建出完整 schema
alembic stamp head       # 已有旧库：标记为已迁移（不必重建数据）
alembic downgrade base   # 回滚
```

`DB_AUTO_CREATE=0` 时关闭代码自动建表，schema 完全交给迁移管理——
`server/database.py` 里那些启动期 `ALTER TABLE` 补丁退化为历史库的兼容兜底。

### 审计日志

删除文档、清空会话、修改密码、登录（含失败）这些**不可逆或敏感**操作
都会写入 `audit_logs` 表（Alembic 迁移 0002），同时输出结构化日志。

- `GET /api/audit`：默认查**自己的**记录；`all_users=true` 需管理员
  （排查"这个文档是谁删的"）
- 两条铁律：**审计写失败绝不能影响业务**（降级为 warning）；
  **detail 不记录密码/token** 等敏感内容，只记录结果与影响
- 登录失败也审计——连续失败是最直接的暴力破解信号

### 评测回归门禁（`.github/workflows/eval.yml`）

手动触发或每周定时跑完整评测，并与基线对比：

```bash
python -m evals.compare evals/reports/ci_baseline.json \
                       evals/reports/latest.json --max-drop 0.05
```

通过率较基线下降超过 5 个百分点即判定失败，阻止合并。

**为什么用整体跌幅而不是逐条回归**：LLM 采样有随机性，同一份代码连跑四轮，

整体跌幅对噪声更鲁棒。逐条排查仍然可用 `--downgrade-only` 手动执行。

## 设计要点

**会话**：Redis key 为 `session:{user_id}:{session_id}`，TTL 默认 7 天
（`SESSION_TTL_HOURS` 可配），按用户隔离。
保存完整 human / ai / tool 序列并保留 `tool_calls`，多轮对话才能延续工具上下文。

**会话侧边栏**：Redis 无法"列出某用户有哪些 key"（KEYS/SCAN 是全库操作），
所以用一个显式索引（`sessions:{user_id}` 哈希）驱动侧边栏。
三个不能省的细节：

1. **标题取首条用户消息且不再变更**（与豆包 / ChatGPT 一致）——
   会话名漂移会让"这个会话是聊什么的"失去锚点；
2. **索引条目比会话本体多活一小时**，列出时逐个 EXISTS 校验并顺手清理死条目，
   否则侧边栏越用越假：列表还在，点进去全是空会话；
3. **新建对话不再删除旧会话**——旧会话由显式删除管理，这是和"清空重来"的本质区别。

**工具安全**：`calculate` 基于 AST 白名单求值，不用 `eval`。拦截函数调用、属性访问、推导式、
文件读取、命令执行，并对幂运算、阶乘、`range` 长度设上限。这是一次真实修复——
原实现直接用 `eval`，等于把 shell 暴露给了 HTTP 接口。

**流式去重**：LangGraph `values` 模式会重复推送同一条消息，后端按内容去重后再下发，前端跳过重复的 human 事件。

**优雅降级**：Redis 异常时记录日志并继续服务，而不是让请求 500。

## 已知局限

- `llm_judge` 判定本身带非确定性，抖动用例里有一部分是评分抖动而非能力抖动。
- 限流目前只有**单用户**维度，未做按 IP 或全局配额；服务已公网部署，这是下一步要补的。
- 并发上限是**进程内**计数，多副本部署时实际并发 = 上限 × 副本数，需要集中式限流时得再改。
- 长上下文压缩采用"摘要"方案，会丢失细节；对必须逐字保留的场景（如法律条款）不适用。
- 图片理解目前只挂在 **react** 架构上，graph 架构尚未接入视觉分支。
- 已上传文件现在可通过删除文档一并清理，但**没有过期清理**，
  长期不删的文件会一直占用磁盘。
- 知识库是**全局共享**的：删除接口只允许删自己上传的文档，
  CLI 入库的共享文档不可通过接口删除（防止一个人误删影响所有人）。
- 语义缓存是**进程内**的，与并发闸门同一取舍：多副本部署时每份实例各有一份缓存，
  且重启即失效。要跨实例共享需要带向量能力的集中存储（如 RediSearch 或专门的向量库）。
- 语义缓存的收益**高度依赖流量重复度**：本项目 demo 场景重复提问很少，
  命中率天然不会高，这项功能真正的价值在于零误命中的安全底线与可量化的延迟降幅。
- 上传目录与会话一样依赖本地单机存储，多副本部署需要换成对象存储。
- 用户表与审计日志已迁移到 MySQL 8；上传文件、知识库、语义缓存仍是单机本地存储，
  多副本部署还需要对象存储与集中式缓存（如 RediSearch）。
- 知识库需要手动执行 `ingest`（现在可以在容器内执行了）。
